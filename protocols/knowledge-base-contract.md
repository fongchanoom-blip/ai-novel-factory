# 五件知识库契约（Knowledge Base Contract）

[REF:protocol.knowledge_base_contract]

## 一、契约定义

本 skill 依赖 **5 件**用户项目内的 Markdown 文件作为"世界事实依据"。每件文件承担明确的角色，缺失时按 [REF:protocol.knowledge_base_contract.ABILITY_DEGRADATION] 降级能力。

```
用户小说项目/
├── 世界基石.md       ← 系统自动维护（初始可空模板）
├── 世界观规则.md     ← 用户必须填写
├── 角色档案.md       ← 用户必须填写
├── 档案事件.md       ← 同人/前传必填，原创可选
└── 文风样本.md       ← 必填，越完整越好
```

---

## 二、每件文件的职责

### 2.1 世界基石.md（World Foundation）

**职责**：项目级事实的"动态权威清单"。由系统根据正文生成自动更新，用户也可手动修正。

**示例内容**：
```markdown
# 世界基石

## 主角当前状态
- 姓名：张三
- 年龄：18 岁
- 修为：筑基期三层
- 拥有的资源：100 灵石、一把剑
- 当前位置：青云宗外门
- 已解锁的能力：透视符箓（每日 3 次）

## 当前主线进度
- 当前卷：第 1 卷
- 当前章：第 12 章
- 主线事件：宗门大比预选赛
- 主线进度：30%（10 章伏笔已埋，3 章已回收）

## 关键剧情状态
- 师姐下落：未知（第 8 章失踪）
- 师父受伤：右臂中毒（已治疗 50%）
```

### 2.2 世界观规则.md（World Rules）

**职责**：不可违反的"硬规则"。例如修仙体系的力量等级、经济规则、地理规则。

**示例内容**：
```markdown
# 世界观规则

## 修仙体系
- 筑基期可使用低阶符箓
- 金丹期才能御剑飞行
- 元婴期寿命 1000 年
- 化神期禁止在凡间出手（天道约束）

## 经济体系
- 1 灵石 ≈ 100 银两
- 1 银两 ≈ 普通人家 1 月开销
- 宗门弟子月俸：10 灵石（外门）/ 100 灵石（内门）

## 地理规则
- 青云宗到最近的城镇需 3 天路程
- 大雪封山期：每年 11 月-次年 2 月
```

### 2.3 角色档案.md（Character Profiles）

**职责**：所有重要角色的详细档案——外貌、性格、动机、关系、知识矩阵。

**示例内容**：
```markdown
# 角色档案

## 张三（主角）
- 外貌：清秀少年，约 17 岁
- 性格：谨慎、机智、有底线
- 动机：为父报仇 + 求道长生
- 关键关系：师姐（暗恋）、师父（敬重）
- 知识矩阵：
  - 知道：师姐失踪真相
  - 不知道：师父真实身份

## 师父（李青云）
- 外貌：中年道人，气度不凡
- 性格：严肃、内敛、对徒弟有温情
- 修为：元婴后期
- 动机：护宗 + 暗中调查张三身世
```

### 2.4 档案事件.md（Event Archive）

**职责**：已发生的重大事件记录（用于一致性核查）。

**示例内容**：
```markdown
# 档案事件

## 第 1 卷主线事件
- 第 1 章：张三入门测试，意外通过
- 第 5 章：张三获得透视符箓
- 第 8 章：师姐失踪，张三开始调查
- 第 10 章：师父受伤，张三发现中毒

## 第 1 卷支线事件
- 第 3 章：张三结识王二，成为好友
- 第 6 章：张三救助受伤妖兽
```

### 2.5 文风样本.md（Style Samples）

**职责**：作者文风样本（语气、句式、词汇偏好）。**最关键**——决定 AI 输出与作者风格的相似度。

**示例内容**：
```markdown
# 文风样本

## 整体风格
- 古风仙侠，略带轻松幽默
- 段落长度：中等（80-150 字/段）
- 对话占比：30-40%
- 第一人称视角（"我"）

## 句式偏好
- 多用四字成语
- 适度使用"罢了""也罢"等古风词汇
- 避免现代网络用语

## 禁用表达
- 不用"懵逼""666""YYDS"等
- 不用"竟然"超过 3 次/章
- 不用"震惊""瞳孔一缩"等夸张描写超过 1 次/章

## 优秀段落示例
> 我深吸一口气，抬手推开那扇破旧的木门。门后是一片漆黑，但我知道，答案就在其中。
```

## 三、能力状态降级表

[REF:protocol.knowledge_base_contract.ABILITY_DEGRADATION]

### 3.1 完整能力矩阵

| 能力域 | 必需文件 | 缺失降级 | 输出模板 |
|--------|----------|----------|----------|
| **选题** | （无） | ✅ 仍可用 | 直接进入选题 |
| **大纲** | 世界观规则.md | ⚠️ 降级 | 引导用户填写世界观规则 |
| **目录** | 世界基石 + 世界观规则 + 角色档案 + 档案事件 | ❌ 禁止 | 引导补齐 4 件文件 |
| **草案** | 世界基石 + 角色档案 + 文风样本 | ❌ 禁止 | 引导补齐 3 件文件 |
| **正文** | **五件全** | ❌ 任一缺失禁止 | 引导补齐缺失文件 |
| **质检** | 至少世界基石 | ⚠️ 降级 | 输出建库模板建议 |
| **存档** | 当前仪表盘或新实体 | ⚠️ 降级 | 输出空状态补丁 |

### 3.2 降级时的输出

```
【能力状态报告】

✅ 选题 — 可用（无需文件）
✅ 大纲 — 可用（依赖：世界观规则.md）
⚠️ 目录 — 降级（缺失：档案事件.md）
   → 仅能生成主线目录，无法保证支线一致性
❌ 草案 — 禁止（缺失：文风样本.md）
   → 必须先提供文风样本才能生成草案
❌ 正文 — 禁止（缺失 2 件：档案事件.md, 文风样本.md）
   → 必须先补齐 5 件文件

【补库建议】
1. 立即补《文风样本.md》—— 提供 2-3 个你认为写得最好的段落
2. 补《档案事件.md》—— 记录已发生的重要事件
```

### 3.3 FATAL_ERROR 触发

当用户**强制执行**禁止操作时：

```
【FATAL_ERROR】

您要求生成【草案】，但《文风样本.md》缺失。

按照 [REF:protocol.knowledge_base_contract.ABILITY_DEGRADATION] 的约定：
- 五件知识库是"事实神谕"的载体
- 没有文风样本，AI 无法保证输出符合您的风格

【建议操作】
A. 立即填写《文风样本.md》（推荐）
B. 跳过 AI 味检测（不推荐）
C. 接受通用风格（可能与您的风格不符）

请选择 [A/B/C] 或补充文件。
```

## 四、契约履约检查

### 4.1 初始化时的检查

在 [REF:core.boot.sequence] 的【第二阶段】执行：

```python
def check_knowledge_base():
    files = {
        'world_foundation': '世界基石.md',
        'world_rules': '世界观规则.md',
        'character_profiles': '角色档案.md',
        'event_archive': '档案事件.md',
        'style_samples': '文风样本.md'
    }
    status = {}
    for key, filename in files.items():
        path = f"{project_dir}/{filename}"
        if os.path.exists(path) and os.path.getsize(path) > 100:
            status[key] = '已绑定'
        else:
            status[key] = '缺失'
    return status
```

### 4.2 热启动时的检查

在 [REF:core.session_state] 的【热启动】状态下：

```python
def hot_check_knowledge_base(last_modified):
    """仅检查自上次启动以来有变更的文件"""
    for filename in kb_files:
        mtime = os.path.getmtime(f"{project_dir}/{filename}")
        if mtime > last_modified:
            trigger_kb_reload(filename)
```

## 六、与其他 skill 的差异

相比 tianming-skill 的契约：
- tianming：要求 5 件文件，但不提供完整模板
- 本 skill：**提供完整模板** + **能力降级表** + **FATAL_ERROR 处理**

相比 webnovel-skills 的契约：
- webnovel：分散在多个 references/ 中
- 本 skill：**统一在 protocol.knowledge_base_contract**
